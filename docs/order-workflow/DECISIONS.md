# Order workflow fix — implementation decisions

Owner-approved scope (2026-09-24): M1 personalized link identity, M2 new-order badge and toast,
M3 continue from context, M4 invoice discoverability. Binding product decision: **D-090** in
`04_DECISIONS.md`. This file records the implementation choices made inside that scope.

| # | Decision | Reason | Files |
|---|---|---|---|
| W-01 | Work branch `fix/order-workflow` from `main` (458d96a). `feature/intelligence-v1` stays separate. | `main` carries the deployed operations and storefront UI and the whole demo path. The intelligence branch is six backend-only commits (owner-only API, no UI, not part of the demo path). It merges cleanly into `main` (checked with `git merge-tree`) and touches none of the files changed here except the decision table, where both only append a row. So it stays separate. Its decision is D-089, so this work uses D-090. | — |
| W-02 | The link → customer association already existed (`customer_access_links`, one active link per customer, hashed secret). No migration. | The server re-resolves the link on every request, so identity can come from it alone. | — |
| W-03 | At checkout a **granted** context sets `orders.linked_customer_id`, `invoices.customer_id` and the first revision's customer. The customer snapshot, prior balance and amount due come from one shared helper, `invoice_editor.apply_customer`, which the invoice editor's create and update paths now also use. It is a pure extraction. | The owner asked to reuse the linking path's logic without calling `orders.link_customer` itself. That action needs an owner actor, writes an owner audit event and creates a new revision. | `services/invoice_editor.py`, `services/checkout.py` |
| W-04 | For a personalized order, the order's contact name and phone come from the customer record. The browser's name and phone are ignored, not merged. `customer_id`, `grade` and `discount` fields stay refused (`extra="forbid"`). | Browser identity must never influence the customer. | `services/checkout.py`, `schemas/checkout.py` |
| W-05 | `contact_name`, `contact_phone` and `contact_address` became optional in the request schema. A public order still needs all three: the API returns 422 `CONTACT_REQUIRED` from the service (previously a schema 422). A personalized order with no address and none saved returns 422 `CONTACT_ADDRESS_REQUIRED`. | A personalized tab no longer sends identity. The public path's outcome (a 422 refusal) is unchanged. | `schemas/checkout.py`, `services/checkout.py` |
| W-06 | The context call adds `has_saved_address`, a boolean for granted contexts only. Checkout shows "Ordering as {display name}" and nothing else about the customer. | Amendments 1 and 5: disclose no more than the context call already did, plus one boolean. | `services/customer_access.py`, `routes/storefront.py`, `schemas/storefront.py`, storefront `CartCheckout.tsx` |
| W-07 | If the link lapses between page load and submit, the API answers 422 `CONTACT_REQUIRED`. The form then switches in place to the public contact fields, shows the notice "This personalized link is no longer active; enter your details to continue.", and the order continues on the public path. | Amendment 2. | storefront `CartCheckout.tsx` |
| W-08 | **Per-tab context.** Each opened link gets its own HttpOnly cookie `tz_customer_{slug}_{ref}`, with the same Secure, SameSite=Lax, path `/{slug}` and 30-day conventions. Verified sessions follow the same pattern: `tz_session_{slug}_{ref}`. `ref` is a 24-hex, domain-separated SHA-256 digest of the link. It is not the secret and not the stored hash. The tab carries `?c={ref}` on every shop link, form and route call. A bare shop address keeps the old meaning, "most recently opened link", through the shop-wide cookie, and pins `c` from then on. An unknown `c` is the public storefront, never another customer. Carts and checkout keys are stored per `{slug}.{ref}`. Exit clears only that context. | Amendment 8: two customers in two tabs of one browser must not change each other. A single shop-wide cookie cannot do that. | storefront `lib/personal.ts`, `lib/format.ts`, `lib/cart.ts`, `lib/shop.ts`, access/checkout/verify routes, pages and components |
| W-09 | The owner's order detail shows "Customer: {name}" for a linked order and no link, select or create controls. The existing `link-customer` endpoint still accepts a received order (a correction path). | Amendment 3. The backend capability is kept intentionally, but the normal UI no longer offers it once an order is linked. | `components/OrdersPanel.tsx`, `routes/storefront.py` (`linked_customer_name`) |
| W-10 | A personalized checkout writes no separate audit event. The order keeps `intended_customer_id`/`intended_assurance`, which records that it came through the link and at which assurance. | There is no actor, and existing order fields already carry the provenance. | `services/checkout.py` |
| W-11 | The badge polls the existing owner order list with `?status=RECEIVED` every 20 s through React Query (`refetchIntervalInBackground`). No new endpoint or column. | That list is owner-only and tenant-scoped, and it already returns id, contact name and creation time, which is enough to diff. The list's existing limit of 100 caps the badge count (F-04). | `components/pendingOrders.ts`, `components/AppShell.tsx` |
| W-12 | New-order detection diffs the current and previous id sets per business. The first answer only sets the baseline. One arrival shows "New order from {contact name}" linking to `section=orders&order={id}`; several show "N new orders" linking to Orders. The notice sits in a polite live region, auto-hides after 15 s and can be dismissed. | The owner's specification. A personalized order's contact name is the customer's name (M1). | `components/AppShell.tsx`, `styles.css` |
| W-13 | The count shows on the Orders entry (desktop rail, More sheet) and on the phone "More" button, because Orders lives under More on phones. The tab title becomes `(n) Tawzeevo Operations`, the existing title with the prefix. | Keeps the existing title and makes the count visible on every layout. | `components/AppShell.tsx` |
| W-14 | The in-panel "N new" counter, taken from notifications that are never marked read, becomes "N awaiting review", computed from the same RECEIVED orders as the badge. The panel no longer calls the notifications endpoint. | Amendment 9: one unambiguous meaning, UI-only, no new notification state. | `components/OrdersPanel.tsx` |
| W-15 | After confirm or decline, `OrdersPanel` invalidates the pending-orders query, so the badge drops immediately. Opening `section=orders&order={id}` opens that order. | "Count drops when the owner confirms or declines"; the notice link must land on the order. | `components/OrdersPanel.tsx`, `components/TenantWorkspace.tsx` |
| W-16 | A shared `NextSteps` block (invoice number link, the existing sharing, "Record payment", "Create delivery") appears on a confirmed order's detail and, after a manual invoice is confirmed, under the invoice document. There, "Record payment" switches to the Payments view in place and the invoice row is omitted, because the document already shows it. | "Continue from context" on the same screen. Every entry only opens an existing page. | `components/NextSteps.tsx`, `OrdersPanel.tsx`, `InvoiceEditor.tsx` |
| W-17 | Section links carry optional `order`, `invoice` and `view` query parameters (`sectionHref`). The Invoices and Deliveries panels are keyed by them, so a link always opens a clean instance. | Deep links without a new router or a special code path. Switching sections drops the parameters. | `components/workspaceSections.ts`, `TenantWorkspace.tsx` |
| W-18 | "Invoice detail" is the existing invoice document in the Invoices section, opened by `invoice={id}`. It loads `GET /api/v1/invoices/{id}` and the customer (`GET /tenants/{t}/customers/{id}`). Only a CONFIRMED or CANCELLED invoice opens; a draft, unknown or foreign id is ignored and the editor stays blank. | Reuses the existing document view. No new invoice page was built. | `InvoiceEditor.tsx` |
| W-19 | An invoice opened by link is read-only (amendment 4). Create revision, cancellation, save, confirm, line editing and item entry are not offered. A note explains this and offers "Start a new invoice". Sharing, payments and balances stay available. | The editor's lines are not loaded for such an invoice, so any line-dependent action would act on empty state. | `InvoiceEditor.tsx` |
| W-20 | Payments opened for an invoice (`view=payments`, or "Record payment" after a manual confirm) selects the existing "Choose amounts" (OWNER) allocation, prefilling that invoice's open amount as both its allocation and the receipt amount. Both stay editable. The invoice row is highlighted with a note. The standalone Payments view keeps its FIFO default. | Amendment 3. No locked rule forces FIFO: the owner may already choose amounts by hand. The command is byte-for-byte the one the owner would send by hand (tested), through the same endpoint and rules. | `InvoiceEditor.tsx` |
| W-21 | Deliveries opened for an invoice list every task state, preselect the invoice in the create form only when it is currently deliverable, and highlight that invoice's tasks. Anything else is ignored. The create command is unchanged. | Resume later: a delivered invoice's task is still found. No special delivery path. | `DeliveryPanel.tsx` |
| W-22 | The order detail response gains `deliveries` (id, status, date of the tasks for the order's invoice). The order detail shows the linked invoice and delivery as links. | Needed to stop and resume from the order. Additive, read-only, tenant-scoped. | `routes/storefront.py`, `schemas/checkout.py`, `OrdersPanel.tsx` |
| W-23 | Invoice references link to the read-only invoice document on the confirmed order's detail and next steps, on delivery entries, and on invoice payment lines. No invoice list exists (F-05). The driver's own work screen is not an owner surface and is unchanged. | M4 scope, operational surfaces only. | `OrdersPanel.tsx`, `NextSteps.tsx`, `DeliveryPanel.tsx`, `InvoiceEditor.tsx` |
| W-24 | Invoice sharing gains "Copy share link" beside the existing WhatsApp and customer-view actions. It is labelled as sharing because the Playwright demo opens the copied link in a new signed-out browser context: it shows the invoice (number and customer, no supplier, cost, grade or driver data), and a forged secret shows only the "link is invalid" message. A clipboard failure tells the owner to copy the field by hand. | Amendment 7, with the verification in `e2e/order-workflow-demo.spec.ts`. | `InvoiceSharing.tsx` |
| W-25 | No deploy. Staging and production both deploy from `main` (staging on push through the Render dashboard setting, live through `deploy.yml` after CI), and there is no staging-only scripted deploy. The work stops after local verification on the branch; nothing was pushed. | The owner's rule: do not deploy to production, and stop if no scripted staging deploy exists. | — |
