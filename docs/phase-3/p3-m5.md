## Synthetic-data demonstration

1. Follow the root README setup. Use a synthetic approved tenant owner and synthetic customer with a valid phone; never paste production data into reports.
2. Create/save an invoice using the existing owner editor. Open **Manage invoice links → Create private link**.
3. Open **Open customer view** in a separate unauthenticated browser. Verify the invoice, switch to Arabic, and inspect RTL. Check that unrelated debt, supplier costs, profit, and history are absent.
4. Open **Share on WhatsApp** and inspect the recipient and prefilled invoice summary/link. Sending remains a deliberate user action. Do not send demo messages to real customers.
5. Replace the link. Reopening the original URL must fail; the replacement must work. Revoke the replacement and verify it becomes unavailable. Keep real capability URLs out of screenshots/logs/reports.
6. For supplier foundation, use `/docs` as the synthetic tenant owner with `tenant_id`: append a USD opening payable of 10, pay 3, verify balance 7, replay the same request/key (still 7), then reverse with a new key/reason (balance 10). Use aware timestamps and decimal strings. Existing tenant supplier IDs come from the tenant's cost-source workflow. No purchase allocation is created.

The shared page shows the **current** revision of exactly one invoice, including draft/cancelled
status when applicable. It does not expose a debt statement or claim payment settlement status.
Order checkout, delivery dates, cancellation-decision messaging, storefront branding expansion,
procurement UI and supplier purchase allocations are not introduced here.

## Operational boundaries

- Anyone holding a capability can read its invoice; treat the link as a secret. The tenant UUID prefix alone grants nothing.
- Link metadata cannot recover a secret. Copy/share it on issuance or replace it later. The public page clears its fragment, so refresh requires reopening the original link.
- Public HTML lives on the existing API origin. Set the existing `VITE_API_BASE_URL` correctly and deploy over HTTPS. No extra provider, payment, or environment variable is required.
- No analytics, external assets, persistent browser token storage, arbitrary HTML rendering, or raw-token database storage is added.
- The bounded rate limiter is per process, not distributed; shared proxies/NATs may share a quota. Multi-worker/global edge limiting and deployed proxy behavior must be audited before scaling.
- Do not capture secret headers or issued-link responses in infrastructure telemetry. Automated application checks do not certify external proxy/hosting logs.
- All database validation uses a disposable local PostgreSQL database. Exact test commands and results are in `RUN_TESTS.md`; P3-M6 still owns full phase-wide E2E/accessibility/reconciliation and deployment-hardening audits.
