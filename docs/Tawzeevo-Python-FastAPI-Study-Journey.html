Login flow

  1. Credentials
  2. Email lookup
  3. Verify hash
  4. Check deleted
  5. Session + JWT

The access token returns in JSON. The opaque refresh token travels only in a scoped HttpOnly cookie and is stored server-side as a hash.

Authenticated request

  1. Bearer token
  2. decode claims
  3. session + user
  4. role dependency
  5. service result

dependencies.py::get_auth_context verifies JWT, session, deletion state, expiry, revocation, and security versions.

Soft delete flow

  1. Lock user
  2. Lock tenants
  3. Protect last owner
  4. Revoke memberships
  5. Mark deleted

No DELETE FROM users. Login, normal listing, and statistics ignore the row; the database record remains.

Tenant approval

  1. Client applies
  2. Admin reviews
  3. Tenant created
  4. Owner membership
  5. Audit event

One transaction commits all steps. The platform administrator does not receive tenant membership.

Suspension / reactivation

  1. ACTIVE
  2. SUSPENDEDbusiness access blocked
  3. data retained
  4. reactivate
  5. same tenant

Temporary non-payment controls access; it never deletes the tenant’s customers, products, or drafts.

Checkpoint SEC-01

Authentication and authorization.

Authentication asks “Who are you?” Authorization asks “What may that identity do?” A valid token is not automatic administrator or tenant-owner access.

System identity

admin and client live on User.type. A system admin controls platform users and tenant lifecycle. Public registration always produces a client.

Tenant authority

owner and driver live on TenantMembership.role. Membership is scoped to one tenant. A platform admin is not automatically an owner.

# Actual Tawzeevo dependency chain (abridged)
Bearer token → decode_access_token → AccessClaims
→ AuthSession + User validation → require_system_admin / require_client
→ resolve_tenant_context → require_tenant_owner

JWT is not the password

The password proves identity during login. Its Argon2id hash stays in PostgreSQL. A JWT is a short-lived signed claim set issued after login. It contains identifiers and expiry—not the password.

Frontend checks are not security

React guards improve navigation, but a caller can bypass React and call the API. FastAPI dependencies enforce authority again on every protected endpoint.

Checkpoint DB-01

Database and migration journey.

PostgreSQL is the durable authority. SQLAlchemy lets Python express rows and queries; Alembic versions the schema. They solve different problems.

Model, schema, service, repository

  1. Pydantic schemaAPI shape and validation
  2. RouteHTTP boundary
  3. Servicebusiness rule + transaction
  4. Repository/querypersistence lookup
  5. SQLAlchemy modeldatabase mapping

A Pydantic schema can reject bad input early, but PostgreSQL constraints still protect data written by another process or concurrent request. Tawzeevo therefore uses both API validation and constraints such as the unique normalized email index, age check, same-tenant foreign keys, and nonnegative money checks.

Migration chain

  1. 0001users, sessions, tenants, applications, audit
  2. 0002platform audit insert policy
  3. 0003customers, categories, tenant products, drafts + RLS

Checkpoint QA-01

Testing from first principles.

A test arranges a known state, performs one action, and asserts an observable result. Tawzeevo combines API tests, real PostgreSQL behavior, authorization negatives, migration/RLS checks, and React component journeys.

Arrange

Fixtures create a disposable database connection, clear tables, and override FastAPI’s get_db dependency.

Act

TestClient sends real HTTP-shaped requests through FastAPI routing, validation, dependencies, services, and SQLAlchemy.

Assert

Tests check status codes, safe response fields, database state, session revocation, tenant isolation, and invariants such as “one active tenant must retain an owner.”

Why PostgreSQL matters

SQLite cannot prove PostgreSQL enums, row locks, RLS, JSONB, or PostgreSQL-specific migration behavior. The Phase 1 integration suite therefore requires a disposable PostgreSQL database.

Quick revision mode

Explain this project

30 seconds

Tawzeevo is a multi-tenant Cash Van operations platform. Phase 1 delivers a FastAPI and PostgreSQL backend, safe registration and JWT sessions, administrator user management, public statistics, tenant approval and lifecycle controls, plus a tenant-isolated customer, category, barcode-product, and draft-invoice slice. The React client is bilingual and uses the real API. Storefront ordering and later operational modules remain future work.

60 seconds

Tawzeevo separates system identity from tenant authority. Users are admin or client; approved clients receive owner membership in a tenant through an audited application transaction. FastAPI routes stay thin, Pydantic validates contracts, services own rules, SQLAlchemy talks to PostgreSQL, and database constraints plus RLS defend tenant boundaries. Login uses Argon2id, a 15-minute access JWT, and a rotating hashed refresh session in an HttpOnly cookie. Soft deletion preserves records and blocks login, lists, and statistics, while transactional last-owner protection prevents an active tenant from becoming ownerless. Phase 1 also includes the React operations UI and a real database-backed Cash Van draft slice.

2 minutes

The browser sends typed requests to FastAPI. A request body is validated by a Pydantic schema before a route calls a service. Authentication dependencies decode the bearer JWT, load the server-side session and user, and reject expired, revoked, deleted, or security-version-mismatched identities. Authorization then checks system role or resolves an active tenant membership. Services use explicit tenant predicates and transactions; PostgreSQL adds unique/check/foreign-key constraints and forced row-level security. Alembic owns the three-migration Phase 1 chain. The original assignment routes—registration, login, profile, admin CRUD, pagination, filters, soft deletion, and statistics—are all present. Tawzeevo extends them with application approval, suspension/reactivation without deletion, last-owner protection, and an approved-owner customer/catalog/draft slice. The isolated role gallery added afterward is synthetic and calls no API, so it is demonstration assistance, not proof of production behavior.

Boundary DEMO-01

Production versus demonstration.

Two different demo mechanisms exist and neither should be confused with unimplemented product scope.

Database demo seeder

apps/api/tawzeevo_api/cli/seed_demo.py uses the real SQLAlchemy models and requires an existing approved owner tenant. It creates synthetic customer, category, tenant-product, and draft rows in the real Phase 1 API model. It proves only those already-implemented slice capabilities.

Role gallery

apps/operations-web/src/demo/ and the gated /demo branch are memory-only presentation code added after Phase 1. They mount before authentication, make no API/database call, write no browser storage, and are not evidence of storefront or delivery implementation.

Production Phase 1

Authentication, users, statistics, tenant applications/lifecycle, tenant isolation, customer/category/tenant-product/barcode, and draft-invoice APIs plus the operations client are real application behavior.
